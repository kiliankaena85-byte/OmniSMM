# LLM Mutation Testing & Adversarial Red Teaming

## Назначение и границы (Overview & Scope)
Скилл `llm-mutation-testing` обеспечивает глубокую проверку качества и полноты тестового покрытия критического кода OmniSMM (WalletOps, ExactMath, Drip-Feed Floor) с помощью мутационного анализа.

---

> **Стандарт платформы OmniSMM 1.0 (2026)**  
> **Фундаментальный закон:** Покрытие кода строками (Code Coverage) — это иллюзия надежности. Зеленый тест, не способный упасть при намеренном искажении бизнес-логики, бесполезен и опасен. Качественный тест-сьют обязан обнаруживать и «убивать» семантические мутации с коэффициентом **Mutation Score $\ge 85\%$** в критических модулях (Tier 1).

---

## 1. Концепция Мутационного Тестирования (Mutation Testing)

### 1.1. Проблема ложноположительного доверия (False Confidence)
Традиционный тест может выполнять 100% строк функции, но проверять лишь одно тривиальное утверждение. Если разработчик или AI случайно поменяет знак вычисления баланса, удалит фильтр `tenantId` или нарушит проверку инварианта Drip-Feed Floor, такой поверхностный тест останется зеленым.

### 1.2. Решение: AI-Диверсант (Adversarial Mutator)
В кодовую базу вносятся искусственные контролируемые дефекты (**Мутанты**):
1. **Мутатор (Mutator Engine):** Инвертирует логические условия, искажает финансовую математику, убирает изоляцию или ломает транзакции.
2. **Прогон тестов (Test Runner):** На каждом мутанте запускается соответствующий тестовый набор (`vitest`).
3. **Классификация исходов:**
   - 💀 **KILLED (Убит):** Тест упал с ошибкой. Мутант обезврежен — тест доказал свою эффективность.
   - 🧟 **SURVIVED (Выжил):** Тест прошел успешно при сломанной логике. Обнаружена критическая слепая зона в тестах!
   - ⚠️ **TIMEOUT / CRASH:** Зацикливание или ошибка компиляции (невалидный мутант).

## 3. Матрица Семантических Мутаторов

| Категория мутации | Тип мутации | Исходный код | Мутант (Дефект) | Ожидаемый убийца (Test) |
| :--- | :--- | :--- | :--- | :--- |
| **Финансы (ACID)** | Инверсия знака | `balance + amountKopecks` | `balance - amountKopecks` | `wallet-ops.test.ts` |
| **Финансы (ACID)** | Нарушение Ledger | `await tx.ledgerEntry.create(...)` | `// Ledger omitted` | `ledger-reconciliation.test.ts` |
| **Финансы (ExactMath)** | Подмена округления | `ExactMath.calculateOrderCostKopecks` | `Math.floor(qty * price)` | `exact-math.test.ts` |
| **Безопасность** | Стирание тенанта | `where: { id, tenantId }` | `where: { id }` | `multi-tenant-isolation.test.ts` |

## 4. Жесткие Инварианты (Hard Invariants)

1. **Инвариант изоляции и отката (Clean-Revert Invariant):**
   Мутации применяются строго в памяти или с гарантированным 100% восстановлением оригинального файла в блоке `finally`. Запрещено оставлять мутированный код на диске.
2. **Порог прохождения гейта (Mutation Threshold):**
   Для финансового ядра (`src/lib/wallet-ops.ts`, `src/lib/exact-math.ts`) и вебхуков эквайринга минимально допустимый Mutation Score:
   $$\text{Mutation Score} \ge 85\%$$
3. **Запрет тривиальных тестов (No Hollow Assertions):**
   Тесты, проверяющие только отсутствие исключений (`expect(() => fn()).not.toThrow()`) без верификации измененного состояния БД, признаются дефектными.

## 5. Премортем-анализ и моделирование отказов

| Сценарий отказа | Вероятность x Влияние | Механизм защиты в коде |
| :--- | :--- | :--- |
| **Мутант вызвал бесконечный цикл** | Средняя x Высокое | Каждый прогон Vitest изолирован жестким таймаутом `timeout: 10000ms`. Зависший тест принудительно убивается и помечается как `TIMED_OUT`. |
| **Сбой отката файла при ошибке скрипта** | Низкая x Критическое | До применения мутации создается физическая резервная копия `.bak`. Перехватчики сигналов `SIGINT`/`SIGTERM` восстанавливают оригинал. |
| **Синтаксически невалидная мутация** | Низкая x Низкое | Перед запуском тестов AST-валидатор компилирует мутированный файл в памяти (`ts.transpileModule`). Если есть синтаксическая ошибка, мутант отбраковывается как `INVALID_SYNTAX`. |

## 6. Чеклист верификации (Verification Checklist)

- [ ] Запущен движок мутаций: `npm run test:mutation`.
- [ ] Проверено финансовое ядро (`ExactMath`, `WalletOps`).
- [ ] Все сгенерированные мутанты классифицированы (`KILLED` / `SURVIVED`).
- [ ] Ни один мутант не выжил в модулях Tier 1 (0 Survived Mutants).
- [ ] Mutation Score $\ge 85\%$.
- [ ] Сформирован официальный протокол `.planning/MUTATION_TEST_REPORT.md`.
- [ ] Все оригинальные файлы восстановлены без изменений (`git status --porcelain` чист).

## Пошаговый алгоритм выполнения (Step-by-step Protocol)
1. **Шаг 1:** Анализ контекста задачи и определение границ влияния.
2. **Шаг 2:** Проверка соответствия архитектурным инвариантам.
3. **Шаг 3:** Реализация изменений с соблюдением контрактов.
4. **Шаг 4:** Верификация через автоматические тесты и линтеры.
5. **Шаг 5:** Документирование и сохранение точки стабильности.

---

## Предотвращаемые антипаттерны (Gotchas / Bad vs Good)
❌ **Плохо:** Игнорирование архитектурных инвариантов ради быстрой реализации.
- ✅ **Хорошо:** Строгое соблюдение чистоты слоев и контрактов платформы.
❌ **Плохо:** Отсутствие автоматических тестов на граничные условия.
- ✅ **Хорошо:** Покрытие сценариев тестами до выкатки изменений.
