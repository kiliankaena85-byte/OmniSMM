# SPEC-2026-09-11: Эшелонированная система защиты от L7 DDoS и ротационных прокси (Echelon DDoS Shield)

## 1. Метаданные спецификации
- **Статус:** PROPOSED (Ожидает согласования)
- **Классификация риска:** Tier 1 (Critical Infrastructure & Availability)
- **Целевые компоненты:** `src/proxy.ts`, `src/lib/security/ddos-shield/`, `src/services/core/rate-limit.service.ts`, Redis, Nginx/Ingress
- **Дата разработки:** 11 сентября 2026 г.
- **Автор:** Fullstack Security Architect

---

## 2. Модель угроз (Threat Model)
- **Вектор атаки:** Постоянный поток в 3 000+ запросов/сек или запросов/мин через пул распределенных резидентных/мобильных/датацентровых прокси (10 000+ уникальных IP).
- **Цели атакующего:**
  1. Исчерпание пула соединений PostgreSQL (`prisma.$connect`), вызывающее падение базы данных и отказ в обслуживании (503 Service Unavailable).
  2. Перегрузка Event Loop Node.js за счет динамического SSR-рендеринга страниц.
  3. Непрерывный парсинг каталога услуг и котировок цен для демпинга.
  4. Брутфорс и учетный перебор (Credential Stuffing) на эндпоинтах авторизации.
- **Почему не работает классический IP Rate Limit:**
  При ротации прокси каждый отдельный IP отправляет не более 1–2 запросов в минуту, что находится ниже любого безопасного порога блокировки по IP.

## 3. Архитектура 5 эшелонов обороны (Defense-in-Depth)

```
[Интернет / 3000 RPS через прокси]
               │
               ▼
┌────────────────────────────────────────────────────────┐
│ ЭШЕЛОН 1: Сетевой фильтр и Ingress (Nginx / Tailscale)  │ ◄── Отсечение Max Conns, Body Size,
└──────────────────────┬─────────────────────────────────┘     белый список поисковых ботов
                       │
                       ▼
┌────────────────────────────────────────────────────────┐
│ ЭШЕЛОН 2: Edge Header Anomaly & Fingerprint (proxy.ts) │ ◄── Client Hints, Sec-Fetch,
└──────────────────────┬─────────────────────────────────┘     Global Header Hash Token Bucket
                       │
            (Подозрительный трафик)
                       │
                       ▼
┌────────────────────────────────────────────────────────┐
│ ЭШЕЛОН 3: Stateless Proof-of-Work (Altcha Challenge)   │ ◄── 50ms CPU нагрузка на атакующего,
└──────────────────────┬─────────────────────────────────┘     выдача __Host-gatekeeper куки
                       │
              (Легитимный трафик)
                       │
                       ▼
┌────────────────────────────────────────────────────────┐
│ ЭШЕЛОН 4: In-Memory кэш & Prisma Bulkhead Isolation    │ ◄── Отдача витрины из RAM (<0.5ms),
└──────────────────────┬─────────────────────────────────┘     Circuit Breaker на пул БД
                       │
                       ▼
┌────────────────────────────────────────────────────────┐
│ ЭШЕЛОН 5: Ловушки (Honeypot) & HTTP Tarpit             │ ◄── Скрытые ссылки /api/v1/sync,
└────────────────────────────────────────────────────────┘     удержание сокетов атакующего
```

### Эшелон 1: Сетевой рубеж и Ingress (Ingress Perimeter)
- **Лимиты параллельных TCP-сессий:** Ограничение до 50 одновременных соединений на класс сети /24.
- **Белый список валидных ботов (Good Bots Whitelist):**
  Криптографическая проверка IP-диапазонов официальных поисковых роботов (Яндекс, Googlebot, Mail.ru) через `rdns` (reverse DNS lookup), чтобы защита никогда не блокировала индексацию SEO.
- **Платежные вебхуки (Payment Webhooks Exemption):**
  Эндпоинты `/api/webhooks/yookassa`, `/api/webhooks/cryptobot`, `/api/webhooks/robokassa` защищаются строгой проверкой HMAC-подписей и исключаются из капч и PoW-челленджей.

### Эшелон 2: Edge Fingerprint & Header Anomaly Engine (`src/proxy.ts`)
- **Вычисление браузерного отпечатка (Header Hash Fingerprint):**
  На уровне Edge для каждого входящего запроса вычисляется:
  $$H = \text{SHA256}(\text{UA} + \text{Accept-Language} + \text{Sec-Ch-Ua} + \text{Header-Order})$$
- **Пул-лимитер по отпечатку (Fingerprint Token Bucket):**
  Даже если IP меняется при каждом запросе, пул запросов с идентичным отпечатком заголовков лимитируется как единое целое в Redis:
  Ключ: `ddos:fp:{tenant}:{H}`, лимит: не более 120 запросов/мин на отпечаток для неавторизованных гостей.
- **Детекция аномалий браузера (Client Hints Cross-Check):**
  - Несовпадение платформы: `User-Agent: Windows`, но `sec-ch-ua-platform: "Android"`.
  - Отсутствие `Sec-Fetch-Dest` при обращении к HTML-страницам браузером Chrome.
  - Порядок заголовков, характерный для библиотек `requests`, `aiohttp`, `Go-http-client`.

### Эшелон 3: Бессерверный Proof-of-Work (Altcha / Cryptographic Challenge)
- **Принцип работы:**
  При фиксации аномалий или превышении порога пула запросов сервер вместо 403 или капчи возвращает легковесный HTML (размер $< 1.5\text{ KB}$) с криптографической задачей PoW (Proof-of-Work):
  $$\text{SHA256}(\text{salt} + \text{number}) \text{ заканчивается на } N \text{ нулей}$$
- **Экономика атаки:**
  - Обычный браузер пользователя решает задачу за ~30–50 мс на Web Worker в фоновом режиме.
  - Атакующий ботнет на 3 000 RPS вынужден тратить $3000 \times 0.05\text{ c} = 150\text{ секунд CPU}$ в секунду, что мгновенно перегружает и выводит из строя серверы злоумышленника.
- **Gatekeeper Token:**
  После решения задачи клиенту устанавливается подписанная HMAC-кука:
  `__Host-gatekeeper={payload}.{hmac}` со сроком жизни 30 минут. Все последующие запросы с этой кукой проходят напрямую без повторных проверок.

### Эшелон 4: Кэширующий буфер (Absorption Buffer) и защита базы данных
- **RAM-витрина (Zero-DB Hit):**
  Все публичные страницы каталога, услуг и категорий кэшируются в памяти процесса (In-Memory LRU) и Redis со стратегией `stale-while-revalidate`.
  Сервер Next.js отдает их из оперативной памяти за **0.3–0.8 мс**, выдерживая до 10 000 RPS без единого запроса к Prisma/PostgreSQL.
- **Database Connection Pool Bulkhead:**
  - Пул Prisma строго ограничен (`connection_limit: 25`).
  - При превышении 75% емкости пула немедленно активируется деградация: запросы поиска и тяжелые фильтры неавторизованных пользователей сбрасываются с `429 Too Many Requests`, гарантируя 100% доступность БД для авторизованных клиентов, оформления заказов и биллинга.

### Эшелон 5: Ловушки (Honeypots) и HTTP Tarpit
- **Honeypot-ссылки:**
  В DOM главной страницы и каталога внедряется невидимая ссылка:
  ```html
  <a href="/api/v1/internal-sync" style="display:none" tabIndex="-1" aria-hidden="true" rel="nofollow"></a>
  ```
  Парсеры и краулеры атакующего переходят по всем ссылкам страницы.
- **Авто-бан в Redis:**
  Любой запрос к `/api/v1/internal-sync` автоматически заносит IP-адрес и Header-Fingerprint в черный список `blacklist:ddos:{id}` на 24 часа.
- **HTTP Tarpit («Вязкое болото»):**
  Для адресов из черного списка ответ выдается чанками по 1 байту каждые 5 секунд с открытым TCP-сокетом. Это приводит к исчерпанию пула свободных сокетов на прокси-серверах атакующего, выводя их из строя.

## 4. Спецификация структур данных и контрактов

### 4.1. Redis ключи
| Ключ | Тип | TTL | Назначение |
| :--- | :--- | :--- | :--- |
| `ddos:fp:{tenantId}:{fpHash}` | Sorted Set (Sliding Window) | 120s | Скользящее окно лимитов по отпечатку заголовков |
| `blacklist:ddos:ip:{ip}` | String ("1") | 86400s (24ч) | Блокировка IP, попавшего в Honeypot |
| `blacklist:ddos:fp:{fpHash}` | String ("1") | 86400s (24ч) | Блокировка сигнатуры бота, попавшего в Honeypot |
| `ddos:pow:challenge:{challengeId}` | String | 300s (5 мин) | Хэш выданной задачи Proof-of-Work |

### 4.2. DTO верификации Proof-of-Work (Zod)
```typescript
export const powVerificationSchema = z.object({
  challengeId: z.string().uuid(),
  salt: z.string().min(16).max(64),
  nonce: z.number().int().nonnegative(),
  signature: z.string().min(64).max(64), // HMAC-SHA256
});
```

## 5. Анализ радиуса поражения (Impact Radius) и Pre-Mortem
1. **Риск 1: Ложное срабатывание на легитимных пользователях за NAT (один офис/провайдер).**
   - *Защита:* Авторизованные пользователи с валидной сессионной кукой `__Host-session_token` полностью освобождены от глобальных отпечатков и PoW.
2. **Риск 2: Блокировка поисковых систем (SEO).**
   - *Защита:* Официальные роботы Яндекса и Google идентифицируются по белому списку доверенных User-Agent с обязательной валидацией rDNS (`.yandex.ru`, `.googlebot.com`).
3. **Риск 3: Сбой платежных вебхуков.**
   - *Защита:* Роуты `/api/webhooks/**` исключены из middleware-фильтрации фингерпринтов и валидируются строго по собственным криптографическим подписям.
4. **Аварийный выключатель (Kill-Switch):**
   - Переменная `DDOS_SHIELD_ENABLED=false` в `.env` мгновенно отключает эшелонированный фильтр без перезапуска контейнеров (hot-reload через Redis config).
