## 1. Контекст инцидентов и Root Cause Анализ

### Инцидент №1: Раскрытие оптового поставщика и сетевых инструкций в личном кабинете
Клиент в личном кабинете (`/dashboard/orders`, мобильный список, всплывающие подсказки `title`) увидел критическую системную строку:
```text
[GATEWAY_SSRF_BLOCKED] Ошибка поставщика [Поставщик: Vexboost]: Private IP blocked. Проверьте корректность URL шлюза поставщика в админке, DNS-резолв или работу сетевого прокси-сервера Clash/Mihomo.
```

**Анатомия нарушения:**
1. **White-Label Breach & Business Risk:** Клиент видит первоисточник услуг (`Vexboost`), что позволяет обойти сервис и лишает платформу статуса независимого провайдера.
2. **CWE-209 (Information Exposure Through Error Message):** Раскрыты внутренние сетевые инструменты (`Clash/Mihomo`, `URL шлюза в админке`, `DNS-резолв`, `SSRF`).
3. **Trust Boundary Violation:** Служебное поле БД `Order.error`, предназначенное для оператора техподдержки, отдавалось на фронтенд напрямую без санитайзера/проекции.
4. **Второй скрытый канал утечки — финансовый леджер (`LedgerEntry.reason`):** В `order.service.ts` метод `failOrderTerminalFast` генерирует описание возврата клиенту: `Авто-возврат (Fail-Fast): Заказ #... отменен из-за ошибки провайдера. Причина: ${reason}`. Это отображается в `/dashboard/finance` в истории платежей.
5. **Дефект статуса `PENDING_CHECK`:** Заказ на проверке отображался с красной ошибкой, выпадал из канбан-доски `FluxOrdersKanban` (не входил ни в одну колонку) и не имел явной вкладки фильтра.

### Инцидент №2: Экран сервисного обслуживания (Maintenance Mode) не отображался пользователям
При включении тумблера «🔴 Включен» в `/admin/settings`:
1. **UX Trap формы:** Модальное окно переключало только локальное состояние React `setMaintenance(true)` и показывало уведомление, но не отправляло Server Action в БД. Реальное значение в БД оставалось `maintenanceMode = false`.
2. **Фильтр тестовых доменов:** В `src/app/layout.tsx` переменная `isTestDomain` включала проверки `host.includes('.ts.net') || host.includes('tailscale')`. В результате официальный туннель платформы Tailscale Funnel всегда обходил Maintenance Screen, даже если в БД стояло `true`.
3. **Docker Build Boundary:** Контейнер `smmplan_web` работал на предыдущей сборке, требуя пересборки/перезапуска после обновления кода.

## 2. Архитектурный контракт и требования (RAC-2026)

### 2.1. Инвариант Zero Vendor Leak (Абсолютный запрет утечки)
- **Правило 1:** Любое упоминание имен провайдеров (`Vexboost`, `Soc-Rocket`, `Likedrom`, `SmmPrime` и любых других), технических тегов (`[GATEWAY_SSRF_BLOCKED]`, `[INSUFFICIENT_PROVIDER_BALANCE]`, `[PRICE_DRIFT_HOLD]`) и инструкций оператора (`Clash/Mihomo`, `админка`, `DNS-резолв`) КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО к передаче клиенту в любых клиентских интерфейсах.
- **Правило 2 (Сохранение данных для оператора):** Поле `Order.error` в базе данных сохраняет полную техническую информацию для панели оператора (`/operator/dashboard/components/failed-orders.tsx`), админ-панели и классификатора ошибок. Очистка производится строго на уровне представления (Presentation Gate) через безопасный трансформер `getCustomerFacingOrderError`.
- **Правило 3 (Статус PENDING_CHECK):** Для заказов со статусом `PENDING_CHECK`, `PENDING` или `PROVISIONING` клиентский санитайзер возвращает `null` — для клиента заказ находится на плановой автоматической проверке, красные плашки сбоя скрываются, бейдж отображается спокойным янтарным цветом: «На проверке».
