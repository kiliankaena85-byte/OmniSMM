# Реестр и Стандарт Спецификаций (Spec-Driven Development — SDD)

> **Стандарт платформы OmniSMM 1.0 (2026)**  
> **Единое правило:** Сначала Документация/Спецификация (`docs/specs/`) $\to$ Затем Тесты (Red Phase) $\to$ Только потом Код (Green Phase).

---

## 1. Трехуровневая классификация рисков (Risk-Tiering)

Для предотвращения бюрократического паралича и сохранения высокой скорости разработки все задачи разделяются на 3 уровня критичности:

| Уровень (Tier) | Зона ответственности | Протокол разработки | Обязательные артефакты |
| :--- | :--- | :--- | :--- |
| **Tier 1: Critical** | Финансы, баланс (`WalletOps`), леджер, оформление заказов, Drip-Feed, миграции БД, очереди BullMQ, аутентификация, вебхуки платежей. | **100% SDD + TDD** (Spec $\to$ Red Tests $\to$ Code $\to$ Green) | 1. Файл спецификации в `docs/specs/`<br>2. Автотесты в `src/__tests__/`<br>3. Согласование человеком |
| **Tier 2: Standard** | Новые страницы админки/кабинета, Server Actions, API роуты, сложные формы и фильтры каталога. | **Light-SDD + Contract Tests** (Спека типов $\to$ Тесты контракта $\to$ Код) | 1. Файл спецификации в `docs/specs/`<br>2. Unit/Integration тесты<br>3. Согласование человеком |
| **Tier 3: Cosmetic** | Правка стилей Tailwind, опечатки в текстах, замена иконок, верстка существующих макетов. | **Direct Implementation + Visual Audit** | 1. Запись в плане<br>2. Визуальный аудит (Puppeteer/браузер) |

---

## 2. Жизненный цикл задачи (SDD-TDD Lifecycle)

```
[ 1. СПЕЦИФИКАЦИЯ ] ──▶ [ 2. СОГЛАСОВАНИЕ ] ──▶ [ 3. RED ТЕСТЫ ] ──▶ [ 4. GREEN КОД ] ──▶ [ 5. СИНХРОНИЗАЦИЯ ]
docs/specs/*.md        Human Approval          *.test.ts (FAIL)       Реализация в src/       CURRENT_STATE.md
Zod DTOs + Invariants  «Согласовано»           Проверка контрактов    Тесты переходят в PASS  ADR & GraphRAG
```

1. **Фаза 1 (Спецификация):** Агент создает файл `docs/specs/SPEC-<YYYY-MM-DD>-<slug>.md` по эталонному шаблону ниже.
2. **Фаза 2 (Согласование):** Человек проверяет контракты, инварианты и граничные условия. Без команды *«Согласовано»* переход к коду **заблокирован**.
3. **Фаза 3 (Red Tests):** Пишутся тесты (Vitest / Playwright). Тесты запускаются и **обязаны упасть** (или зафиксировать отсутствие методов), доказывая, что они действительно валидируют будущий код.
4. **Фаза 4 (Green Code):** Пишется минимально необходимый код в `src/`. Тесты переходят в `PASS`. Проверяется `tsc --noEmit` (0 ошибок) и отсутствие утечек секретов.
5. **Фаза 5 (Синхронизация):** Статус спеки меняется на `IMPLEMENTED`, обновляется `CURRENT_STATE.md`.

## 3. Матрица состояний и Инварианты (State Machine & Invariants)
- **Допустимые состояния:** `[STATE_A] -> [STATE_B] -> [STATE_C]`
- **Запрещенные переходы:** какие мутации блокируются на уровне бизнес-логики.
- **Инварианты надежности:** ExactMath (копейки BigInt), Ledger-First, Drip-Feed Floor, изоляция `tenantId`.

## 4. Матрица граничных условий (Edge Cases Matrix)

| Сценарий | Входные данные | Ожидаемое поведение | Код ошибки / Статус |
| :--- | :--- | :--- | :--- |
| **Happy Path** | Валидный запрос, достаточный баланс | Создание записи, списание, возврат данных | `200 OK / { success: true }` |
| **Zero/Negative Balance** | `balance < amount` | Блокировка мутации, откат транзакции | `{ success: false, error: 'INSUFFICIENT_FUNDS' }` |
| **Concurrent Race (TOCTOU)** | 2 параллельных запроса с одним ID | Один проходит, второй отклоняется (409) | `409 Conflict / P2002` |
| **Network Timeout** | Таймаут провайдера > 5000ms | Circuit Breaker, сохранение в Outbox | `{ success: false, error: 'GATEWAY_TIMEOUT' }` |
| **Invalid Auth / IDOR** | Чужой `userId` или пустая сессия | Немедленный отказ Fail-Closed | `401 Unauthorized / 403 Forbidden` |
