# Multi-Model Jury System (Коллегия Присяжных из Гетерогенных LLM)

> **Стандарт платформы OmniSMM 1.0 (2026)**  
> **Фундаментальный закон:** Ни одна языковая модель не обладает монополией на истину. Каждое архитектурное семейство LLM страдает специфическими «слепыми зонами» (Cognitive Blindspots). Критические решения и изменения платформы (Tier 1/Tier 2) обязаны проходить слепую валидацию коллегией из 3 независимых моделей разных архитектурных школ с правом абсолютного вето.

---

## 1. Концепция Гетерогенного Слепого Консенсуса

### 1.1. Проблема однородных нейросетевых ошибок (Monocultural Failure)
Если код пишет модель семейства Claude, а проверяет Checker на базе Claude — обе модели разделяют идентичные байасы внимания:
- Склонность доверять словесным описаниям в комментариях.
- Сходные пробелы в валидации многопоточных race conditions в Node.js / BullMQ.
- Одинаковое восприятие синтаксических конструкций TypeScript и ORM Prisma.

### 1.2. Решение: 3 Присяжных из Независимых Семейств
1. **Присяжный A — OpenAI Architecture (o3-mini / GPT-4o):**
   - **Специализация:** Строгая логика, дискретная математика, многопоточные гонки (TOCTOU, Row-Level Locks), формальная верификация типов.
2. **Присяжный B — Anthropic Architecture (Claude 3.7 Sonnet):**
   - **Специализация:** Архитектурные границы (Clean/Hexagonal Architecture), Next.js 16 App Router инварианты, эргономика API, Server/Client boundary.
3. **Присяжный C — Open-Weights Deep Reasoning (DeepSeek-V3 / NVIDIA Nemotron 550B):**
   - **Специализация:** Состязательный пентест (Adversarial Red Team), BOLA/IDOR уязвимости, обход бизнес-логики, проверка регулярок на ReDoS.
4. **Резервный Арбитр — Google DeepMind (Gemini 2.5 Flash / Gemini 3 Flash):**
   - **Специализация:** Анализ контрактов, сверка со спецификациями, синтез итогового арбитражного решения при сбоях внешних шлюзов.

## 3. Жесткие Инварианты (Hard Invariants)

1. **Инвариант слепого ревью (Blind Review Invariant):**
   Модели оценивают задачу независимо, в параллельных сетевых потоках. Ни одна модель не имеет доступа к промежуточным выводам других присяжных до момента агрегации.
2. **Инвариант абсолютного вето (Zero-Blocker Veto Rule):**
   Даже если 2 модели поставили оценку 10/10 и вердикт ACCEPT, но 3-я модель обнаружила реальный дефект класса BLOCKER (например, утечка баланса, отсутствие CSRF/IDOR проверки, Transaction Escape), релиз **БЛОКИРУЕТСЯ БЕЗУСЛОВНО**.
3. **Порог супербольшинства (Supermajority $\ge 2/3$):**
   Для получения статуса APPROVED требуется минимум 2 вердикта ACCEPT из 3 при среднем балле консенсуса $\ge 8.0/10$.
4. **Инвариант машиночитаемого отчета (Structured Machine-Readable Output):**
   Каждый присяжный обязан вернуть строгий JSON по Zod-схеме JuryVerdictSchema. Парсинг устойчив к рассуждениям <think>...</think> и markdown-блокам.
5. **Обязательный артефакт в репозитории:**
   Каждый прогон жюри сохраняет протокол голосования в .planning/jury_verdicts/JURY_VERDICT_<TIMESTAMP>.json и читаемый markdown в docs/architecture/JURY_VERDICTS.md.

## 4. Премортем-анализ и моделирование отказов (Failure Scenarios)

| Сценарий отказа | Вероятность x Влияние | Механизм защиты в коде |
| :--- | :--- | :--- |
| **Сбой или таймаут одного из провайдеров API** | Высокая x Среднее | Движок использует умный Fallback Pool: при недоступности OpenAI/Claude автоматически подключается резервный арбитр Gemini 3 Flash / Nemotron. |
| **Галлюцинация несуществующего блокера (False Blocker)** | Средняя x Среднее | Арбитр-синтезатор сопоставляет строчку кода и AST: если файл или строка не существуют в git diff, блокер помечается как INVALID_HALLUCINATION и отклоняется. |
| **Застревание в нерешаемом споре моделей** | Низкая x Высокое | Лимит раундов арбитража = 2. При неразрешимом разногласии решение эскалируется человеку-разработчику (Human Approval Gate). |
