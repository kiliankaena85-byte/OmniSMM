# cgroups v2 Memory Controller & Docker Runtime Internals

## 1. Архитектура cgroups v2 vs cgroups v1

Начиная с современных версий Linux-ядер (5.8+) и Docker Engine 20.10+, стандартной подсистемой изоляции ресурсов стала **cgroups v2 (Unified Hierarchy)**.

### Ключевые отличия, влияющие на память:
1. **Единая иерархия (Unified Hierarchy):** В v1 подсистемы `memory`, `cpu`, `blkio` управлялись независимыми деревьями. В v2 память и сброс кешей на диск связаны напрямую — ядро точно знает, какой процесс генерирует дисковые операции при нехватке памяти.
2. **Устранение `--oom-kill-disable`:** В cgroups v1 можно было заблокировать OOM Killer для контейнера, что часто приводило к зависанию всей ноды или kernel panic. В cgroups v2 эта опция **игнорируется**.
3. **Устранение `--kernel-memory`:** Память ядра (dentries, inodes, socket buffers, page tables) в cgroups v2 учитывается бесшовно в общем пуле cgroup.

## 2. Иерархия файлов и лимитов памяти cgroups v2

Вся статистика и управление контейнером находятся в псевдо-файловой системе:
- **Systemd-драйвер (по умолчанию в Ubuntu/Debian/RHEL):**
  `/sys/fs/cgroup/system.slice/docker-<CONTAINER_FULL_ID>.scope/`
- **Cgroupfs-драйвер:**
  `/sys/fs/cgroup/docker/<CONTAINER_FULL_ID>/`

### Основные управляющие файлы:

| Файл cgroups v2 | Соответствие Docker | Описание поведения ядра |
| :--- | :--- | :--- |
| `memory.current` | Текущий фактический объем | Полный объем памяти, занятый контейнером (anon + file + slab + sock). |
| `memory.min` | Жесткая защита | Гарантированный минимум RAM, который ядро **никогда не отберет** даже при глобальном OOM хоста. |
| `memory.low` | `--memory-reservation` (Soft Limit) | «Мягкая защита». Если хост под давлением, ядро пытается забрать память у других групп, прежде чем трогать эту. |
| `memory.high` | Порог троттлинга | При превышении этого порога процесс **не убивается**. Ядро замедляет (троттлит) аллокации процесса и принудительно заставляет его сбрасывать кеши. |
| `memory.max` | `--memory` (Hard Limit) | Жесткий потолок. При превышении ядро запускает прямой синхронный reclaim; если память освободить не удалось — вызывается OOM Killer. |
| `memory.events` | Счетчики аварий | Файл со счетчиками: `low`, `high`, `max`, `oom`, `oom_kill`. |
| `memory.stat` | Детальная структура | Побайтная разбивка: анонимная память, файловый кеш, kernel stack, slab. |

## 3. Ловушка `docker stats`: почему контейнеры падают при «60% RAM»

Очень частая ошибка DevOps-инженеров — доверие процентам в `docker stats`.

### Формула `docker stats`:
$$\text{MemoryUsage}_{\text{docker stats}} = \text{memory.current} - \text{inactive\_file}$$

В выводе `docker stats` вычитается неактивный файловый кеш (`inactive_file`), потому что считается, что ядро может легко его сбросить. 

### В чем опасность (The Catch):
1. Если контейнер активно пишет на диск (например, логи приложения, SQLite, временные файлы загрузок `multer/formidable`, Redis AOF append-only log), страницы памяти переходят в состояние **`active_file` (Dirty Cache)**.
2. Грязные страницы (`dirty pages`) **нельзя сбросить мгновенно** — их нужно сначала сбросить на диск через дисковый ввод-вывод (`sync`).
3. Если диск медленный или загружен, ядро не успевает сбросить `active_file` до поступления нового запроса на аллокацию памяти.
4. В результате: `memory.current` упирается в `memory.max`, ядро не может освободить память за отведенный квант времени и **вызывает OOM Killer**, убивая контейнер.
5. При этом в мониторинге оператор видит, что `docker stats` показывал всего 60% памяти!

### Истинная проверка через `memory.stat`:
```bash
cat /sys/fs/cgroup/system.slice/docker-<ID>.scope/memory.stat
```
Обращайте внимание на:
- `anon`: Реальная оперативная память процесса (куча Node.js, буферы Postgres). Не может быть сброшена на диск без Swap!
- `file`: Страницы файлов, закешированные в RAM.
- `file_dirty`: Страницы, ожидающие записи на диск. Если это значение велико — узким местом является дисковый I/O.

## 4. PSI — Pressure Stall Information (Метрика давления памяти)

В современных ядрах Linux доступен файл `memory.pressure`:
```bash
cat /sys/fs/cgroup/system.slice/docker-<ID>.scope/memory.pressure
```

Вывод содержит две строки:
```
some avg10=0.00 avg60=0.00 avg300=0.00 total=0
full avg10=0.00 avg60=0.00 avg300=0.00 total=0
```
- **`some`**: Процент времени, когда ХОТЯ БЫ ОДИН тред контейнера простаивал в ожидании освобождения памяти.
- **`full`**: Процент времени, когда ВСЕ треды контейнера полностью заблокированы и ждут память (полная остановка сервиса).
- **Критический порог:** Если `some avg10 > 25.0` или `full avg10 > 5.0` — контейнер находится в состоянии острого кризиса памяти и вскоре будет убит OOM Killer.
