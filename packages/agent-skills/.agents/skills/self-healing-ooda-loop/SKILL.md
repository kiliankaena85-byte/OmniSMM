# Closed-Loop Autonomous Self-Healing & Telemetry OODA Loop (OODA-2026)

> **Стандарт платформы OmniSMM 1.0 (2026)**  
> **Фундаментальный закон:** Время реакции на инцидент (MTTR) не должно зависеть от человеческого бодрствования. Любое критическое необработанное исключение платформы обязано проходить 4-фазный цикл OODA: от детекции до изолированного падающего теста и проверенного хотфикса с передачей решения на Human Approval Gate.

---

## 1. Концепция 4 Фаз Цикла OODA

```
                   [ НЕОБРАБОТАННОЕ ИСКЛЮЧЕНИЕ / СБОЙ В ПРОДЕ ]
                                        │
                                        ▼
      ┌───────────────────────────────────────────────────────────────────┐
      │   ФАЗА 1: OBSERVE (НАБЛЮДЕНИЕ & ОЧИСТКА ДАННЫХ)                   │
      │   - Перехват из Sentry / Redis Stream / SecurityAlertService      │
      │   - Дедупликация и троттлинг алертов                              │
      │   - Жесткая санитизация PII (emails -> u***, IPs -> ***.***)      │
      └───────────────────────────────────────────────────────────────────┘
                                        │
                                        ▼
      ┌───────────────────────────────────────────────────────────────────┐
      │   ФАЗА 2: ORIENT (ОРИЕНТАЦИЯ & РЕПРОДУКЦИЯ — RED PHASE)           │
      │   - Парсинг стектрейса и локализация модуля                        │
      │   - Автогенерация воспроизводящего теста (src/__tests__/repro/)    │
      │   - Запуск теста: подтверждение сбоя (TEST MUST FAIL — RED)       │
      └───────────────────────────────────────────────────────────────────┘
                                        │
                                        ▼
      ┌───────────────────────────────────────────────────────────────────┐
      │   ФАЗА 3: DECIDE (РЕШЕНИЕ & СИНТЕЗ ХОТФИКСА)                      │
      │   - Анализ корневой причины (Root Cause Analysis)                 │
      │   - Синтез минимального диффа (Minimal Invasive Hotfix)           │
      │   - Оценка радиуса поражения (Impact Blast Radius mapping)         │
      └───────────────────────────────────────────────────────────────────┘
                                        │
                                        ▼
      ┌───────────────────────────────────────────────────────────────────┐
      │   ФАЗА 4: ACT (ДЕЙСТВИЕ, ВЕРИФИКАЦИЯ & HUMAN GATE)                │
      │   - Применение патча к кодовой базе                               │
      │   - Повторный запуск теста: подтверждение починки (GREEN)         │
      │   - Контроль сборки: npx tsc --noEmit (0 ошибок)                  │
      │   - Формирование отчета SELF_HEALING_INCIDENT_REPORT.md           │
      └───────────────────────────────────────────────────────────────────┘
                                        │
                                        ▼
                             [ HUMAN APPROVAL GATE ]
                           «Одобряю выкатку хотфикса»
```

## 2. Жесткие Инварианты и Антипаттерны (Hard Invariants & Anti-Patterns)

1. **ТАБУ №1: No-Test Hotfix (Слепой хотфикс):**
   - ❌ **ЗАПРЕЩЕНО** применять хотфикс в код без предварительно созданного падающего теста, воспроизводящего данный инцидент.
2. **ТАБУ №2: PII Leakage in Logs / LLM Prompts:**
   - ❌ **ЗАПРЕЩЕНО** передавать реальные клиентские данные (номера карт, пароли, сырые email-адреса, токены или IP-адреса) во внешние языковые модели или логи. Все данные перед анализом проходят PII Redaction.
3. **ТАБУ №3: Autonomous Production Deployment (Самовольный деплой):**
   - ❌ **ЗАПРЕЩЕНО** автоматически выкатывать сгенерированный патч в рабочий боевой контейнер (`:3000`) без прямого подтверждения человека через Human Approval Gate.
4. **ТАБУ №4: Over-Engineering Scope Creep:**
   - ❌ **ЗАПРЕЩЕНО** в рамках самовосстановления переписывать смежные архитектурные слои. Хотфикс обязан быть минимальным ($\le 20$ строк) и узконаправленным.

## 3. Премортем-Анализ и Моделирование Отказов (Failure Scenarios)

| Сценарий отказа | Вероятность x Влияние | Защитный механизм OODA |
| :--- | :--- | :--- |
| **Синтезированный хотфикс ломает смежный модуль (Регрессия)** | Средняя x Высокая | После применения фикса запускается не только тест репродукции, но и проверка типов `tsc --noEmit` и Maker-Checker линтеры. |
| **Шторм повторяющихся ошибок переполняет память (Alert Flood)** | Высокая x Средняя | Встроен скользящий дедупликатор алертов в Redis (`security:alert:throttle:`) с окном 60 секунд на пару (event + trace). |
| **Тест репродукции не падает на исходном коде (False Negative)** | Низкая x Высокая | Если сгенерированный тест проходит на сломанном коде, контур немедленно останавливается с вердиктом `REPRO_FAILED` и передает управление инженеру. |

## 4. Чеклист Верификации (Verification Checklist)

- [ ] Инцидент перехвачен и дедуплицирован.
- [ ] Все PII-данные в логе обезличены.
- [ ] Создан изолированный тест репродукции `src/__tests__/repro/repro-<id>.test.ts`.
- [ ] Тест запущен на исходном коде и гарантированно упал (**RED PHASE CONFIRMED**).
- [ ] Разработан минимальный обратно-совместимый хотфикс.
- [ ] Хотфикс применен, и тест репродукции перешел в **GREEN PHASE**.
- [ ] `npx tsc --noEmit` выполнен без единой ошибки (0 TS errors).
- [ ] Сформирован машиночитаемый и человекочитаемый отчет `.planning/SELF_HEALING_INCIDENT_REPORT.md`.
